# Todo — 포인트로 서로의 할 일을 사고파는 개인 프로젝트

Spring Boot(Kotlin) 기반 백엔드 프로젝트입니다. 할 일 관리 기능에 "포인트로 서로의 할 일을 사고판다"는 거래 기능을 얹어서, 여러 사용자가 동시에 같은 자원을 건드릴 때 생기는 문제(중복 처리, 데드락, 성능 저하)를 직접 만들고 고쳐보는 걸 목표로 만들었습니다.

**1인 프로젝트입니다** — 기획, 설계, 구현, 테스트, 부하테스트까지 전부 혼자 진행했습니다. 안드로이드 개발자로 일하다가 백엔드로 방향을 바꾸기 위해 시작했습니다.

## 1. 이 프로젝트는 무엇을 하나요?

- 할 일을 만들고, 수정하고, 지우고, 완료 체크를 할 수 있습니다.
- 할 일에 카테고리를 붙일 수 있습니다 (여러 개 가능, 안 붙여도 됨).
- 로그인한 사용자는 자기 할 일만 보고 관리할 수 있습니다.
- 포인트를 충전하고, 그 포인트로 다른 사람이 등록한 할 일을 살 수 있습니다.
- 자주 조회되는 데이터는 Redis 캐싱으로 응답 속도를 높입니다.

## 2. 가장 공들인 부분 — 동시에 여러 사람이 몰려도 안전하고 빠르게

여러 사람이 동시에 같은 사람의 포인트를 충전하거나, 같은 할 일을 사려고 하는 상황을 실제 부하테스트(k6)로 재현하면서 아래 문제들을 순서대로 찾고 고쳤습니다.

- 동시에 충전하면 한쪽의 변경이 사라지는 문제(lost update)를 재현 → 낙관적 락과 재시도 로직을 추가해 우선 해결.
- 그 상태로 부하테스트를 하다가 MySQL이 실제로 데드락을 일으켜 트랜잭션을 강제 종료시키는 걸 발견 → `SHOW ENGINE INNODB STATUS` 로그를 분석해 원인(두 계정에 접근하는 순서가 거래 방향에 따라 뒤바뀌는 것)을 찾고, 접근 순서를 정렬해 해결.
- 데드락은 해결됐지만, 이번엔 재시도가 몰리면서 충전 실패율이 4.7%까지 오르는 새 문제가 생김 → 실행계획, 락 대기시간, 커넥션 풀을 하나씩 확인한 끝에 진짜 원인이 재시도 구조 자체라는 걸 확인 → 재시도 로직을 없애고 DB에서 한 번에 처리하는 원자적 업데이트로 바꿔 해결.
- 결과: 응답 속도가 중앙값 기준 최대 4배, p99 기준 최대 2배 빨라졌고, 부하테스트에서 초당 446건(TPS)을 실패 없이 처리하는 것까지 확인했습니다.

## 3. 기술 스택

| 분류 | 사용 기술 |
| --- | --- |
| 언어 / 프레임워크 | Kotlin, Spring Boot |
| 데이터 | MySQL, JPA/Hibernate, Redis |
| 동시성 제어 | Redisson 분산락, 낙관적 락(`@Version`), DB 원자적 UPDATE |
| 인증 | JWT |
| 테스트 | JUnit5, Mockk/Mockito, 통합 테스트 전용 Redis·DB 환경 |
| 부하테스트 / 모니터링 | k6, Spring Actuator |
| 배포 | Docker, Docker Compose |

## 4. 왜 이렇게 만들었나

기능을 한 번에 완성하기보다, 문제를 재현하고 → 로그·지표로 원인을 확인하고 → 고치고 → 다시 부하테스트로 검증하는 과정을 반복하는 데 집중했습니다. 동시성 문제가 실제로 어떻게 발생하고, 어떻게 진단해서 고치는지를 직접 경험해보고 싶어서 만든 프로젝트입니다.

> Docker Compose 설정에 다중 인스턴스·Swarm 관련 설정이 포함돼 있지만, 이는 학습 목적으로 구성해본 것이며 실제 오토스케일링/고가용성을 검증한 것은 아닙니다.

## 5. 실행 방법

실행 시 `.env` 파일이 필요합니다.

### 로컬 개발용

| 명령어 | 설명 |
| --- | --- |
| `make local-up` | 로컬 개발 환경 컨테이너 실행 (`docker-compose.override.yml` 포함) |
| `make local-down` | 로컬 개발 환경 컨테이너 중지 및 삭제 |
| `make restart-local` | 로컬 컨테이너 재시작 (= down 후 up) |

### 프로덕션 배포용 (테스트 겸용)

| 명령어 | 설명 |
| --- | --- |
| `make prod-up` | 서버 이미지 pull 후 프로덕션 컨테이너 실행 |
| `make prod-down` | 프로덕션 컨테이너 종료 및 삭제 |
| `make restart-prod` | 프로덕션 컨테이너 재시작 |

### Docker Swarm 기반 스택 운영 (학습 목적)

| 명령어 | 설명 |
| --- | --- |
| `make stack-up` | Docker Swarm 초기화 후 스택 배포 (`todo-stack` 이름 사용) |
| `make stack-down` | Docker Swarm 모드 종료 |
| `make stack-ps` | 현재 배포된 스택 내 서비스 상태 확인 |
